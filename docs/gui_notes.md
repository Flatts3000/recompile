## Keep machine GUIs to a minimum

**The mod keeps machine GUIs to a minimum, on purpose.** The Sorting Tarp was deliberately rewritten to be stateless: right-click it holding garbage to sift drops into the world, no GUI, no internal inventory, no hopper automation. Any block that stores items or opens a machine screen is a design reversal - check `../trashlands/docs/design_decisions.md` before adding one. Most containers reuse a vanilla screen: the Scrap Barrel reuses `ChestMenu`, and the Burn Barrel (a furnace-variant) reuses `FurnaceMenu` - neither mints a bespoke screen.

**Each custom screen is a recorded exception.** Derive the current set from `client/*Screen.java` (every one extends `client/gui/LayoutScreen`), not from a count written in prose.

**The pattern that has actually emerged: containers reuse a vanilla screen; producers with a gauge, a picker or an output vanilla has no shape for cannot.** Energy bars, tank gauges and pickers have no vanilla equivalent to borrow. The rule that binds is that each one is a deliberate call written down, not that there is only ever one: **no new custom machine screen** without recording a reversal; reuse a vanilla screen when you can.

Notes that do not fit a table cell:

- **Hydroponics Bay.** A chest screen for its slots plus Jade for the gauges would have obeyed the minimal-GUI rule without reversing it, since Jade already reports the nursery's water and the generators' FE. The owner called for a real GUI (2026-08-02) because the bay is the only machine consuming water AND power at once, so "why is it not running" has two answers, and three resources on hover is worse than three gauges in front of you.
- **Cupola Furnace.** Its menu reimplements the slots, `quickMoveStack` and the progress data sync over a bare `AbstractContainerMenu`. Leaving `BlastFurnaceMenu` cost two things, and both are settled (#240): vanilla's **recipe book** and **JEI's furnace transfer button**. Neither was a defect of the slot; both were integrations the borrowed menu supplied for free. The JEI half was rebuilt (#244) - a transfer handler is twenty lines and its absence reads as "this recipe is uncraftable" rather than "this button is missing". The recipe book half is a standing decision; see [below](#the-recipe-book-is-not-coming-back).
- **Slag Furnace and Sintering Kiln do NOT get the recipe book or JEI's transfer button back** by subclassing the vanilla menu. Both belong to the SCREEN rather than the menu (vanilla's furnace screens build their own recipe-book component; ours extend `AbstractContainerScreen` via `LayoutScreen`), and JEI's furnace transfer handler keys on vanilla's menu classes rather than subclasses of them. #240's account of what the Cupola gave up against a *vanilla* furnace stands; it is not something these machines recover. A menu subclass saves reimplementing a menu, and that is the whole of it.
- **Sell and Buy Terminals are one recorded reversal, not two.** The earlier proposal was GUI-less selling plus recipe-based buying, specifically to avoid minting screens, and it was reversed because no vanilla screen shows a price. Neither terminal has a block entity, a container or power - the balance is a data attachment on the player and the sell grid is menu-local like a crafting grid - so they are outside `MachineParityTests` and `checkContainersDeclareCapabilities` by construction.
- **Hauler Depot's button** is one control with two wire ids (`DEPLOY_BUTTON`, `RECALL_BUTTON`) rather than a toggle, so a laggy double-click cannot deploy and then immediately recall.
- **Freight Terminal** is the first screen here whose contents arrive in the open buffer rather than in data slots: requirements do not change while it is open, and a quota may run to 100,000 (`FreightPhaseRecipe`'s `count` range), which a 16-bit data slot cannot carry.

## The recipe book is not coming back

**The recipe book is not coming back, and that is a standing decision rather than a backlog item** (owner, 2026-08-19): *no recipe-book buttons in this mod's machines.* So do not reimplement `RecipeBookMenu` for the Cupola, and do not reach for vanilla's `AbstractFurnaceScreen` on a machine merely because its menu would fit - the book comes with it. It also explains a thing that would otherwise look like an oversight: `VitrifyingRecipe.isSpecial()` returns true, keeping obsidian out of every recipe book, and with no book of our own to serve there is nothing lost by that.

## The GUI framework

**Every custom screen runs on the GUI framework** (`com.flatts.recompile.gui` + `com.flatts.recompile.client.gui`, spec `docs/gui_framework_spec.md`, #164). **A machine declares its screen once, as a `ScreenLayout`, and the menu places slots from that declaration rather than from numbers of its own.** That is the whole point: slot coordinates used to be baked into `Slot` objects in the menu while the drawing that had to line up with them lived in a client-only class, with nothing connecting the two - the Burner Generator shipped with its FE readout drawn straight through its own fuel row, and the Tree Nursery's screen declared `FERT_X = 44` while its menu independently passed `44` to a `Slot`. The rules that bite:

- **The declaration is common code and rendering is a client-side visitor over it.** A menu is constructed on a dedicated server, so nothing in `gui/` may import `net.minecraft.client`. This is a deliberate choice, not the only option - **owo-lib solves the same problem the other way**, letting a client layout move slots after the menu has placed them (sound, since a click sends a slot *index*, so coordinates are purely visual). We keep the truth server-side because that is what lets `MenuLayoutTests` measure it; adopting owo's shape would leave those tests measuring numbers the client overwrites. owo has a live `26.1-Neo` branch on 26.1.2 and is MIT, so this was a real decision - it also needs mixins, which this mod has none of, and would be a hard runtime dependency.
- **`imageWidth`/`imageHeight` are final and pass through a 5-arg `super(...)`, so a layout must be computable before the screen object exists.** Hence a pure declaration in a `static final LAYOUT`, never something accumulated while rendering.
- **A static `LAYOUT` that transitively touches a registry-backed class cannot be named from another class's static initialiser during mod construction.** `MenuLayoutTests` referencing `TreeNurseryMenu.LAYOUT` eagerly pulled in `TreeNurseryBlockEntity`, whose static `FluidResource.of(Fluids.WATER)` throws *"Components not bound yet"* - and the whole mod fails to load with a bare `ExceptionInInitializerError`. Hold suppliers, not layouts.
- **26.1 renders through a retained-mode "extract" model, and exactly one class still knows it.** `GuiGraphicsExtractor`, drawing in `extractBackground(...)` (not `renderBg`), `blit` with a `RenderPipelines` pipeline + explicit atlas dims. That lives in `client/gui/VanillaGui`, which is also the only place a screen's chrome comes from; `GuiFrameworkDisciplineTest` fails the build if a screen mentions a pipeline, a blit, or even `leftPos`. Before it, three screens carried a private `panel()`/`slot()`/`recess()` that approximated vanilla rather than borrowing it, so the mod shipped two panels that did not look alike.
- **A menu data slot is 16 bits on the wire, whatever its Java type says.** `ClientboundContainerSetDataPacket` keeps its value in an `int` field and then writes it with `writeShort` and reads it back with `readShort` - so a synced number over 32,767 reaches the screen wrapped negative, and one over 65,535 truncated. Nothing logs it and the server stays right, so the only symptom is a screen quoting a number the player knows is wrong. Synced values were long under the ceiling by accident rather than by design - a tank or an FE buffer capped at 20,000 or less at their DEFAULTS - until the market's scrip balance, which runs to a billion and so travels as two slots recombined on the client (`content/menu/WideSync`, used through `BalanceSync` and pinned by `MarketBalanceSyncTest`). **The defaults are not what a pack gets; the config ranges are.** #369 measured it: eight config values have a maximum above 32,767 and five of them feed a data slot - the Bay's grow ticks, tank and battery, and the Nursery's cook ticks and tank. The reported symptom was one arrow; the same defect was live on the Nursery's arrow and all four gauges, unreported, because a default never reaches the ceiling and only a pack retune exposes it.

## Sync what the screen displays

**The rule that came out of it: sync what the screen DISPLAYS, not the quantity behind it.** An arrow draws a proportion, so `WideSync.permille` sends thousandths and one slot always suffices whatever the goal. A tooltip printing millibuckets needs the millibuckets, so those go as two halves. A countdown printing seconds sends seconds, which fit. Applying it made the Bay's progress cost one slot instead of two.

**Two related traps sit next to it.** A client must not recompute a synced value from `RCConfig`, which is COMMON and therefore NOT synced by NeoForge - the Tree Nursery was reading its cook total that way, so a client whose config file differed drew the arrow against a number the server never agreed to. And **the ceiling is not only 16 bits**: the Bay sizes its battery as `growTicks * fePerTick`, whose maxima multiply to 24 billion and wrapped NEGATIVE as an `int` at about 8,947 FE a tick, so the battery accepted nothing and the machine silently never ran. `MenuWireCeilingTest` pins all of it at the config maxima, applying the same `(short)` narrowing the packet performs.

## Verifying screens and the guidebook

**Screens are the one layer GameTest and JUnit are blind to.** Geometry is asserted server-side and the layout algebra has unit tests, but a gauge filled from the wrong end passes both. `python tools/shoot_screens.py` opens every screen in its `SCREENS` list in a running `runClient` and screenshots them - that is the acceptance evidence. A new screen belongs in that list. **The guidebook was in the same blind spot and is now covered too**, by `python tools/shoot_guidebook.py`, which walks every category and every entry in the book data (`data/recompile/modonomicon/books/guide/`) and fails if any of them does not open as ITSELF (#259). That gap is how #241 went unnoticed: every paragraph break in every text page of the book (71 at the time) was swallowed, so paragraphs ran together, and it shipped that way for releases while `GuidebookTests` - which proves a lang key exists and an icon resolves - passed throughout.

**Both `shoot_guidebook.py` and `shoot_screens.py` open their screens with devbridge's `use` verb** (the second ported 2026-09-04, while screenshotting the market terminals). `click` drives a screen that is already up and refuses when none is, so before `use` the only way in was synthesizing an OS-level mouse event through PowerShell - which needed the game window foregrounded and silently did nothing when it was not: a run of the old tool reported all ten screens it then covered as "opened nothing" while the game sat behind a terminal, and `use` opened every one on the first try. `use` is a real right-click: it mirrors vanilla's own ordering (entity, then block, then the item in the air), waits for the screen because a container's arrives a tick later on a packet, and names what was in hand so an empty hotbar slot is distinguishable from an item that opened nothing. That last distinction matters here more than anywhere: holding nothing used to report exactly the same "no screen opened" as a page that failed to draw.

**Entry nodes are not widgets.** Category buttons are, and `screen` reports a click point for each, so the rail is never computed. Modonomicon draws the entry nodes itself, so their positions come from the book data - every entry JSON carries a grid `x`/`y` on a fixed lattice - and `shoot_guidebook.py` requires each predicted click to actually open an entry, so a stale calibration fails loudly rather than photographing empty parchment.
